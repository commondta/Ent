How each item is worked

No blind sweeps across the codebase. One form, one module, one process — and each runs the whole gate before the next one starts.

01

Understand — read that item's real controller, view, entity, stored procedures and approval path. No extrapolating from a sibling module.

02

Document — every field, endpoint, state transition and calculation, with worked examples, into docs/modules/.

03

Research and feasibility — cost, dependencies, risks, alternatives, and a stated recommendation.

04

Task breakdown — concrete implementable steps written into the plan.

05

You review — work stops here. Nothing is built until you have read it and said go. This is the single control that stops a business rule being reproduced wrongly.

06

Build, verify, close — against the Definition of Done, then the next item, and not before.

Active item — module and navigation architecture

Before more forms are rebuilt, they need somewhere coherent to land. Every form in the system has now been located, measured and assigned to a module — and the way users reach them has been redesigned around how large ERP systems actually organise this.

What the audit found

  • Folders carry no meaning. 209 real forms across 32 view folders. Home alone holds 50 forms from eight unrelated domains — Block, Property Setup, Construction Monitoring, Map Approval, Clearance, Demarcation, Stock Creation.
  • The menu is 243 KB of hard-coded Razor — 22 top-level groups, nested four levels deep, 200 links pointing at only 178 distinct targets.
  • A fake subtree. Administration → Reports → MemberReports lists Floor, Features, Finishes and Sector — the setup items, pasted in. The whole branch is a copy-paste, and two sibling branches under it are the same paste.
  • Broken links shipped to users. "Transfer Set Receiving" opens the Site Plan. "Drawing Scrutiny Charges" opens Demarcation Request. Two "Finger Uploader" links call an action that does not exist. A form named ChargesGroupFormTest is in the live menu as "Charges Incorporation Setup".
  • Fifteen working forms are unreachable — KYC, Deal Merger, Dealer Reservation, Booking Backlog, Purchase Request, Map Design, Re-Design, Admin Dashboard and seven more. They exist, they work, nothing links to them.
  • The structural finding: Permissions.FormName is a string and the layout checks Html.UserHavePermission("<menu label>") — so the menu label is the permission key. PermissionForms is flat: no parent, no module, no hierarchy. Renaming a menu item silently revokes access for every role, and there is no module concept anywhere in the data model.

  • Every form has exactly one home — a module, a sub-area, and one item type: workspace, transaction, inquiry, periodic run, report or setup.
  • Doing work and configuring the system look different. Setup is always last on a module page, below a rule. It also appears in one flat Configuration index under Administration, so an administrator never walks twelve modules — same rows, two views.
  • Batch runs are separated from single transactions on purpose. An operator must never reach a run that bills thousands of records while looking for one bill.
  • The approval inbox is pinned above the modules, not inside one. It is the most-used screen in the system and today it is not in the sidebar at all.
  • It is all data. Adding a form, a sub-area or a whole module is an insert — no shell code changes. Moving a form between modules keeps its permission key, so nobody loses access.

What the analysis found

  • 16 defects in ~630 lines. Create and update share one endpoint. Delete is a GET. Four separate null-reference crashes wait on a missing row. Created_By = block.Created_By is a self-assignment, so the audit trail is whatever the browser sent.
  • The page needs no login at all — HomeController carries no [Authorize], and it serves about 50 screens.
  • The view fights itself — validation checks a field that is not on the form, all four AJAX calls are synchronous, and the submit handler is re-bound on every save.
  • Database trap: Block is a SQL Server temporal table. History is already captured at the database level, so the migration squash at #46 destroys it unless system-versioning is preserved.
  • Open question D9: three entities reference Block by foreign key; twenty store the block name as free text — and in StockCreation the foreign key was written, then commented out. Asked, not assumed.

Assumptions — and what happens if they are wrong

  • Local only; no production system depends on this repo today. If wrong, the sequencing changes completely and cutover planning moves to the front.
  • The database schema stays compatible and column names are preserved. If wrong, Phase 3 grows an entire data-migration workstream.
  • You review at each gate. If not, the method fails — this is the one control that removes R1.
  • The domain model is worth keeping. If wrong, the strategy becomes a decision to re-take, not an assumption to hold.

Definition of done

A module is not finished until every line is true. The second-to-last one is what stops us ending up maintaining two systems at once.

  • Behaviour spec written and reviewed by you, before any code
  • Domain rules live in the domain layer, not in a controller
  • Every command validated server-side
  • Every endpoint carries a permission policy, enforced on the server
  • Correct HTTP status codes; no exception text ever reaches the caller
  • Unit tests for rules, integration tests for persistence, endpoint tests for authorization
  • Parity-checked against the legacy behaviour, with every difference listed and accepted
  • No new compiler warnings — the build treats them as errors
  • Legacy controller, view and routes removed in the same change
  • docs/modules/<module>.md updated to describe the new behaviour
  • PROJECT.md updated
